# Windrose Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A macOS terminal application (`windrose`) that discovers, scores, and reports every AI option on the user's Mac — local runtimes, Apple platform models, and frontier cloud providers — with a guided `doctor` mode for setup, health, and performance tuning.

**Architecture:** A sync Rust core (no async runtime) with a mockable `Probe` trait per AI provider, a hardware profiler, a scoring engine, and a doctor engine — all UI-agnostic. Two frontends consume that core: a plain CLI (`scan`, `score`, `doctor`, `report`) and a Ratatui TUI using the Elm architecture (Model → Msg → update → view). Distribution via GitHub Releases + Homebrew tap, automated by cargo-dist.

**Tech Stack:** Rust 2024 (MSRV 1.85), clap 4.5 (derive), ratatui 0.29 + crossterm 0.28, ureq 2 (sync HTTP), serde/serde_json, color-eyre, clap_mangen, cargo-dist.

**Related research already in the vault:** [[Spinnaker — Market & Technical Research]] (Apple Foundation Models specifics), [[Axon 1.2–1.3 — Research Notes]] (Ollama + MLX backend behaviour).

## Decisions taken (veto any of these before execution)

- **Name: `windrose`** — a compass rose for navigating AI options; consistent with the nautical family (Spinnaker, Pennon). Repo `jandro/windrose`, tap `jandro/homebrew-tap`.
- **Sync core, no tokio** — probes are short-lived subprocess/HTTP calls run in `std::thread::scope`; async buys nothing here and doubles complexity.
- **ureq over reqwest** — small sync HTTP client for localhost probes (Ollama/LM Studio APIs).
- **cargo-dist** for release automation — it generates the GitHub Release, installers, and the Homebrew formula; the shell scripts wrap it.
- **Privacy stance:** detection reports *presence* of API keys/configs only. Key values are never read into memory beyond an "is set" check, never logged, never displayed.

## Global Constraints

- Rust edition 2024, MSRV 1.85; binary name `windrose`; repo layout is a single crate (no workspace).
- Targets: `aarch64-apple-darwin` (primary) and `x86_64-apple-darwin` (degraded scoring, still functional).
- ratatui `0.29`, crossterm `0.28`, clap `4.5` with `derive`, ureq `2`, serde `1`, color-eyre `0.6`, clap_mangen `0.2`.
- **No live network or real subprocesses in unit tests** — every probe goes through the `SysCtx` mock boundary (Task 2).
- **Plain-language rule:** every user-facing string that names a technology gets a one-line explanation on first appearance (e.g. "Ollama — a free app that runs AI models privately on your Mac"). No unexplained jargon anywhere in the UI, doctor output, or docs.
- **Secrets rule:** presence-only detection of credentials (see decision above). `Detection.details` must never contain a secret value.
- TDD throughout: failing test → minimal impl → pass → commit. Conventional-commit messages (`feat:`, `fix:`, `docs:`, `chore:`).

## Core interfaces (referenced by every task)

```rust
// model.rs
#[derive(Debug, Clone, PartialEq, serde::Serialize)]
pub enum Availability { Ready, InstalledNotRunning, Partial(String), NotFound }

#[derive(Debug, Clone, Copy, PartialEq, serde::Serialize)]
pub enum Category { LocalRuntime, OptimisedRuntime, ApplePlatform, CloudProvider }

#[derive(Debug, Clone, serde::Serialize)]
pub struct Detection {
    pub id: &'static str,           // "ollama"
    pub name: &'static str,         // "Ollama"
    pub category: Category,
    pub availability: Availability,
    pub version: Option<String>,
    pub details: Vec<(String, String)>, // ("Models installed", "llama3.2, qwen3")
    pub friendly: String,           // one-line plain-English explanation of what this is
}

// sys.rs — the ONLY place that touches the OS. Everything else takes &dyn SysCtx.
pub trait SysCtx {
    fn run(&self, cmd: &str, args: &[&str]) -> Option<String>; // stdout on exit 0
    fn http_get(&self, url: &str, timeout_ms: u64) -> Option<String>;
    fn env_is_set(&self, var: &str) -> bool;                   // presence only, never the value
    fn path_exists(&self, path: &str) -> bool;
    fn home(&self) -> std::path::PathBuf;
}

// probes/mod.rs
pub trait Probe: Sync {
    fn id(&self) -> &'static str;
    fn detect(&self, sys: &dyn SysCtx) -> Detection;
}
pub fn registry() -> Vec<Box<dyn Probe>>;
pub fn run_all(sys: &(dyn SysCtx + Sync)) -> Vec<Detection>; // parallel via thread::scope

// scoring.rs
pub struct DeviceScore { pub overall: u8, pub memory: u8, pub compute: u8, pub tiers: Vec<ModelTierFit> }
pub struct ModelTierFit { pub label: &'static str, pub fits: Fit, pub est_tok_s: Option<(u16, u16)>, pub advice: String }
#[derive(PartialEq)] pub enum Fit { Great, Ok, Tight, No }
pub fn score(hw: &HardwareProfile) -> DeviceScore;

// doctor.rs
pub enum CheckStatus { Pass, Warn, Fail }
pub struct FixGuide { pub steps: Vec<String>, pub commands: Vec<String>, pub docs_url: Option<&'static str> }
pub struct CheckResult { pub id: &'static str, pub title: String, pub status: CheckStatus, pub explanation: String, pub fix: Option<FixGuide> }
pub fn health_checks(dets: &[Detection], hw: &HardwareProfile) -> Vec<CheckResult>;
pub fn performance_checks(dets: &[Detection], hw: &HardwareProfile) -> Vec<CheckResult>;
```

### Task 9: On-device scoring engine

**Files:** Create `src/scoring.rs`; docs stub `docs/SCORING.md` (formula + table, written in this task)

**Interfaces:** Produces `score(hw: &HardwareProfile) -> DeviceScore` (types in *Core interfaces*).

- [x] **Step 1: Failing tests:**

```rust
#[test]
fn m4_pro_48gb_scores_high_and_fits_32b() {
    let hw = hw_fixture(ChipTier::Pro, 48, true); // helper building HardwareProfile
    let s = score(&hw);
    assert!(s.overall >= 75);
    assert!(s.tiers.iter().any(|t| t.label == "30B class (Q4)" && t.fits == Fit::Ok));
    assert!(s.tiers.iter().any(|t| t.label == "70B class (Q4)" && t.fits == Fit::No));
}
#[test]
fn intel_8gb_scores_low_with_cloud_advice() {
    let s = score(&hw_fixture(ChipTier::Intel, 8, false));
    assert!(s.overall <= 25);
    assert!(s.tiers.iter().all(|t| t.fits == Fit::No || t.label.contains("3B")));
}
```

- [x] **Step 2: FAIL → implement the formula (document identically in docs/SCORING.md):**
  - **memory (0–100):** usable model RAM = `ram_gb * 0.65`; scored against the 4-bit footprint table: 3B≈2 GB, 7–9B≈5 GB, 13–14B≈9 GB, 30–32B≈19 GB, 70B≈40 GB.
    **Correction — these numbers contradict this task's own tests, verified by running them.** They are
    bare weight sizes; the fit thresholds need *working-set* sizes (weights + conversation + runtime).
    With the literal table, `m4_pro_48gb_scores_high_and_fits_32b` gets `Great` where it asserts `Ok`
    (48 GB × 0.65 ÷ 19 = 1.64, over the ×1.5 Great threshold), and `intel_8gb_scores_low_with_cloud_advice`
    fits the 7B class as `Tight` where it asserts nothing but 3B fits (8 × 0.65 ÷ 5 = 1.04, over ×1.0).
    Implemented footprints are 2.5 / 6 / 10 / 22 / 42 GB, which satisfy both tests and match reality:
    a model whose *file* just fits in memory does not actually run. Score = capped linear scale where 8 GB→30, 16→55, 32→75, 48→85, 64+→95.
  - **compute (0–100):** chip tier base (Intel 10, Base 55, Pro 70, Max 85, Ultra 95) + up to +5 for gpu_cores ≥ 30.
  - **overall:** `min(memory, compute) * 0.6 + max * 0.4` (bottleneck-weighted), −10 if `is_laptop` on Max/Ultra (thermal sustain), floor 5.
  - **tiers:** for each of the five size classes emit `Fit` (Great/Ok/Tight/No from RAM headroom ×1.5/×1.2/×1.0) and `est_tok_s` ranges per tier from a static table (e.g. Base+7B ⇒ (15, 30); Pro+7B ⇒ (30, 55); document sources as "community llama.cpp/MLX benchmarks, indicative only"). Every tier gets a plain-English `advice` sentence ("Runs comfortably — a good everyday choice" / "Won't fit in memory — use a cloud provider for this size").
- [x] **Step 3: Pass. Commit** `feat: on-device scoring engine`.
